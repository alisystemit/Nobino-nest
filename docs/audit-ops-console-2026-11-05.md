# ممیزی خصمانهٔ کنسول عملیات سرور — 2026-11-05

ممیزی سخت‌گیرانهٔ ماژول کنسول عملیات (`/api/admin/ops/*`، تب «عملیات» سوپرادمین،
حلقهٔ گیت push=استقرار) بعد از کامیت `d84541b`. روش: خواندن سطر‌به‌سطر هر سه
لایه (بک‌اند، فرانت، اسکریپت‌های استقرار/داک)، مقایسه با رفتار واقعی nginx و
شاخهٔ واقعی مخزن، و شبیه‌سازی سناریوهای نفوذ/خرابی.

وضعیت: **رفع‌شده** = در همین نشست اصلاح شد؛ **پذیرفته** = رفتار عمدی/بی‌خطر؛
**مستند** = ریسک باقی‌ماندهٔ پذیرفته‌شده.

## یافته‌های بحرانی

### OC-30 — جعل IP از راه X-Forwarded-For و دور زدن همهٔ سقف‌های نرخ
- فایل: `backend/src/lib/rate-limit-lite.ts` (`clientIpFromRequest`).
- مشکل: کد اولین ورودی `x-forwarded-for` را می‌گرفت؛ ولی nginx این پروژه
  (`deploy/nginx/nobino.conf.template`) با `proxy_add_x_forwarded_for` آدرس واقعی
  کلاینت را به **انتهای** لیست اضافه می‌کند. یعنی مهاجم با هدر
  `X-Forwarded-For: 1.2.3.4` هر بار IP تازه‌ای جعل می‌کرد و سقف نرخ
  `ops.console.rate_per_minute` و `deploy_per_hour` را کامل دور می‌زد.
- گستره: همین تابع در ورود ادمین (محافظت brute-force)، تست پیامک، چت هوش مصنوعی
  و نوبت‌گیری هم استفاده می‌شود — همهٔ آن‌ها همین آسیب را داشتند.
- رفع‌شده: اولویت با `X-Real-IP` (nginx بازنویسی‌اش می‌کند) و بعد **آخرین**
  ورودی XFF.
- پیش‌شرط محیطی: اپ باید فقط از پشت nginx دیده شود (در توپولوژی فعلی سرور
  همین‌طور است)؛ اگر روزی :3100 مستقیم به اینترنت باز شود، باید سراغ
  `app.set("trust proxy", ...)` برویم.

### OC-34 — شاخهٔ `main` در اسکریپت و داک‌ها در حالی که شاخهٔ واقعی `master` است
- فایل: `deploy/install-git-remote.sh` (پیش‌فرض `BRANCH`)،
  `docs/ops-console.md` (خطوط 64/70/73)، `docs/deploy.md` (خط 58).
- مشکل: شاخهٔ واقعی مخزن `master` است (تأییدشده از `git log` و
  `/api/admin/ops`). هوک فقط `refs/heads/main` را گوش می‌کرد → اولین
  `git push deploy master` **بی‌صدا هیچ استقراری اجرا نمی‌کرد** و کاربر
  فکر می‌کرد استقرار شده است.
- رفع‌شده: پیش‌فرض `BRANCH="${BRANCH:-master}"` + اصلاح همهٔ نمونه‌های داک.

### OC-35 — هوک push بدون قفل: دو استقرار هم‌زمان + پاک‌سازی‌نشدن روی خطا
- فایل: `deploy/install-git-remote.sh` (بدنهٔ هوک post-receive).
- مشکل: هوک هر push را مستقل در پس‌زمینه `update.sh` می‌کرد؛ دو push نزدیک به هم
  = دو استقرار موازی روی یک دیتابیس/بیلد (ریسک خرابی بکاپ و فایل‌های release).
  ضمناً بلوک پس‌زمینه `set -euo pipefail` را از اسکریپت نصب به ارث می‌برد،
  بنابراین اگر update.sh خطا می‌داد، خط `=== git-push deploy end ===` هرگز
  نوشته نمی‌شد و لاگ «استقرار نیمه‌کاره» را کامل نشان نمی‌داد.
- رفع‌شده: قفل مشترک روی دیسک (`logs/ops-deploy.lock`، همان قفلی که دکمهٔ پنل
  می‌گیرد)؛ push وسط استقرار «skipped» می‌شود (نه استقرار موازی)، و اجرا از
  `scripts/ops-deploy-runner.sh` می‌گذرد که نتیجه را همیشه ثبت و قفل را همیشه
  آزاد می‌کند (بدون `set -e`).

### OC-36 — چک‌اوت مستقیم از مخزن bare، مخزن گیت پوشهٔ اپ را کهنه می‌گذارد
- فایل: همان هوک (دستور `git --work-tree="$APP_DIR" checkout -f`).
- مشکل: checkout از bare فقط فایل‌ها را بازنویسی می‌کرد؛ `.git` خود APP_DIR
  (HEAD/index/origin) به‌روز نمی‌شد → `git status` روی سرور همه‌چیز را
  «تغییریافته» نشان می‌داد و `git pull` دکمهٔ پنل (و هر ابزار گیت دیگر) با
  مخزن ناسازگار کار می‌کرد.
- رفع‌شده: `git -C APP_DIR fetch origin BRANCH && git -C APP_DIR reset --hard FETCH_HEAD`
  — مخزن سرور همیشه آینهٔ دقیق remote است.

### OC-1 — وضعیت «در حال اجرا» فقط در حافظه → استقرار دوم بعد از ری‌استارت
- فایل: `backend/src/lib/ops-console.ts` (`deployState` ماژول‌سینگلتون).
- مشکل: وسط استقرار، update.sh خودش سرویس را ری‌استارت می‌کند (pm2 restart).
  بعد از ری‌استارت `deployState` خالی بود → (الف) کارت «استقرار» وضعیت «آماده»
  نشان می‌داد و دکمه دوباره فعال می‌شد → استقرار دوم هم‌زمان؛ (ب) ممیزی
  `ops.deploy.finish` هم ثبت نمی‌شد (هندلر exit با پروسهٔ قبلی مرده بود).
- رفع‌شده: قفل/متادیتا روی دیسک (`logs/ops-deploy.lock` با pid/started/cmd)؛
  وضعیت از دیسک خوانده می‌شود و با ری‌استارت گم نمی‌شود. pid داخل قفل، pid
  **اجراکنندهٔ** استقرار است (پردازهٔ detached که از ری‌استارت سرویس جان سالم
  به در می‌برد)، پس بررسی «پروسه زنده است» درست کار می‌کند.
- ریسک باقی‌مانده (مستند): اگر اجراکننده با SIGKILL کشته شود، فرزندانش
  (update.sh و بیلد) یتیم می‌مانند و قفل بعد از مرگ pid زودتر از پایان واقعی
  باز می‌شود؛ سقف سن ۲ ساعته پوشش دوم است. کشتن دستی پروسهٔ استقرار عملاً فقط
  با دخالت مستقیم اپراتور رخ می‌دهد.

## یافته‌های مهم

### OC-2 / OC-23 — خواندن بی‌سقف فایل لاگ
- `tailLines` و دم لاگ استقرار در `admin__ops.ts` کل فایل را با
  `readFileSync(..., "utf8")` می‌خواندند. لاگ چندگیگابایتی = فلج شدن حافظهٔ
  سرویس با یک درخواست (و سقف 20 درخواست/دقیقه آن را تشدید می‌کرد).
- رفع‌شده: `tailLines` فقط ۲۵۶ کیلوبایت آخر را می‌خواند (با `readSync` آفست‌دار)
  و هر دو مصرف‌کننده از آن استفاده می‌کنند.

### OC-3 — بررسی مسیر لاگ فقط لغوی (فرار از راه symlink)
- `isAllowedLogPath` پیشوند رشته‌ای را چک می‌کرد؛ یک symlink داخل `logs/`
  به `/etc/passwd` یا هر فایل دیگر، خواندنش را مجاز می‌کرد.
- رفع‌شده: مقایسه روی `realpathSync` هر دو طرف (فایل و پایهٔ مجاز)؛ اگر
  realpath درنیاید → رد.

### OC-5 — مقدار منفی تنظیم سقف، محدودساز را بی‌صدا خاموش می‌کرد
- `numericSettingOrEnv` هر عدد متناهی را می‌پذیرفت؛ `-1` در ستینگ → شرط
  `limit > 0` برقرار نمی‌شد → عملاً «بدون سقف». (۰ = بدون سقف عمدی است؛ منفی
  اشتباه تایپی است.)
- رفع‌شده: مقادیر منفی/نامعتبر → fallback.

### OC-31 / OC-F12 — تشخیص «غیرفعال بودن» با تطبیق رشتهٔ فارسی
- فرانت وضعیت 403 را با `error.includes("غیرفعال")` تشخیص می‌داد؛ تغییر جملهٔ
  بک‌اند (یا خطای دیگری که تصادفاً این کلمه را داشت) دکمهٔ فعال‌سازی را اشتباه
  نشان می‌داد/قایم می‌کرد.
- رفع‌شده: بک‌اند در 403 فیلد `code: "OPS_DISABLED"` می‌دهد و فرانت اول آن را
  چک می‌کند (تطبیق رشته فقط fallback ماند).

### OC-F3 — پیگیری استقرار: سقف ۳۰ دقیقه و یادداشت کهنه
- پولر ۱۰ ثانیه‌ای بعد از ۱۸۰ تلاش بی‌صدا می‌ایستاد و یادداشت «استقرار شروع
  شد» برای همیشه می‌ماند؛ پایان واقعی هم هیچ پیامی نداشت.
- رفع‌شده: پایان استقرار پیام «استقرار پایان یافت…» و رسیدن به سقف، پیام
  «پیگیری خودکار متوقف شد…» می‌گذارد.

### OC-F9 — کدهای رنگی ANSI در `<pre>` تیره
- لاگ update.sh/PM2 پر از escape های رنگی است؛ نمایش خام، متن را ناخوانا می‌کرد.
- رفع‌شده: حذف ANSI قبل از نمایش (هر دو دم لاگ).

## چه چیزهایی درست بود (چک‌شده و تأیید)

- کنترل دسترسی ADMIN روی هر سه مسیر + گیت سوییچ `ops.console.enabled` (403 فارسی).
- الزام `confirm: true` سمت سرور برای استقرار (تأیید دومرحله‌ای UI فقط UX است؛
  بک‌اند هم مستقل چک می‌کند).
- دستور استقرار هرگز از بدنهٔ درخواست ساخته نمی‌شود؛ فقط از ستینگ با
  اعتبارسنجی توکن‌به‌توکن (بدون shell، بدون متاکاراکتر، محدود به داخل پروژه).
- خروجی spawn به فایل لاگ داخل `logs/` (gitignored، بیرون از web root).
- شروع/پایان استقرار در AuditLog.
- ممیزی `apiError` برای خطاهای غیرمنتظره → بدون نشت استک به کلاینت.
- `<pre>` های فرانت با JSX (اسکیپ خودکار React) → بدون XSS.
- update.sh در مسیر عادی هیچ پرامپتی ندارد → اجرای بدون TTY از هوک/پنل امن است.
- فایل‌های gitignored (`.env`، `backups/`، `logs/`) با هیچ push/چک‌اوتی دست نمی‌خورند.
