# کنسول عملیات سرور (ماژول ops-console)

ماژولی که در پنل سوپرادمین روشن/خاموش می‌شود و سه کار می‌کند:

1. **نمایش وضعیت سرور** (فقط‌خواندنی): نسخهٔ نود، آپ‌تایم، حافظه، پینگ دیتابیس، آخرین کامیت گیت، وضعیت PM2 و پرشدگی دیسک.
2. **نمایش دم لاگ سرویس**: آخرین خطوط لاگ PM2 (یا هر فایلی که با `OPS_CONSOLE_LOG_FILE` معرفی شود).
3. **اجرای استقرار با یک دکمه**: همان `deploy/update.sh` با تأیید دو مرحله‌ای؛ خروجی و پایان اجرا در خود تب دیده می‌شود.

همهٔ این‌ها فقط برای نقش **سوپرادمین (ADMIN)** کار می‌کنند و هیچ مسیر «نوشتن فایل» باز نمی‌شود؛ دسترسی شما به من برای ویرایش فایل‌های سرور از راه **حلقهٔ گیت** (بخش ۵) برقرار می‌شود، نه از راه HTTP.

## ۱) روشن‌کردن

1. وارد پنل سوپرادمین شوید: `تنظیمات سیستم` ← بخش «کنسول عملیات سرور».
2. «وضعیت کنسول عملیات» را روی **فعال** بگذارید و ذخیره کنید.
3. تب **«عملیات»** در سایدبار پنل ظاهر می‌شود (وضعیت سرور را همان‌جا می‌بینید).

تا وقتی سوییچ خاموش است، همهٔ مسیرهای `/api/admin/ops/*` با `403` پاسخ می‌دهند.

## ۲) مسیرها و مدل امنیتی

| مسیر | روش | کار |
| --- | --- | --- |
| `/api/admin/ops` | GET | وضعیت سرور/دیتابیس/گیت/PM2/دیسک + وضعیت استقرار |
| `/api/admin/ops/logs?lines=200` | GET | دم فایل لاگ سرویس (حداکثر 500 خط) |
| `/api/admin/ops/deploy` | POST | شروع استقرار — بدنه باید `{"confirm": true}` باشد |

- هر سه مسیر: فقط `ADMIN`، فقط وقتی سوییچ فعال است، با سقف نرخ جداگانه.
- سقف‌ها (قابل تنظیم در همان بخش تنظیمات؛ ۰ = بی‌سقف):
  - `ops.console.rate_per_minute` — درخواست وضعیت/لاگ در دقیقه به ازای هر IP (پیش‌فرض 20).
  - `ops.console.deploy_per_hour` — اجرای استقرار در ساعت به ازای هر IP (پیش‌فرض 3).
- شروع و پایان هر استقرار در **تب حسابرسی** ثبت می‌شود (action: `ops.deploy.start` / `ops.deploy.finish`).
- دستور استقرار از تنظیم `ops.console.deploy_cmd` خوانده می‌شود (پیش‌فرض `deploy/update.sh`) و فقط مسیر نسبی `.sh` داخل پروژه با گزینه‌های `--…` پذیرفته می‌شود — هیچ ورودی آزاد shell اجرا نمی‌شود.
- لاگ فقط از این ریشه‌ها خوانده می‌شود: پوشهٔ پروژه، `~/.pm2/logs`، `/var/log`.

## ۳) دکمهٔ استقرار — دقیقاً چه می‌کند

1. مودال تأیید دو مرحله‌ای: تیک «می‌دانم سرویس قطع می‌شود» + نوشتن کلمهٔ «استقرار».
2. `bash deploy/update.sh` در پوشهٔ پروژه اجرا می‌شود (pull ← `npm ci` ← بیلد ← بکاپ خودکار دیتابیس ← هم‌راستایی schema ← ری‌استارت ← بررسی سلامت).
3. استقرار در پس‌زمینه اجرا می‌شود و **با ری‌استارت سرویس کشته نمی‌شود**؛ خروجی کامل به `logs/ops-deploy-last.log` می‌رود و همان تب، وضعیت و دم خروجی را نشان می‌دهد.
4. اگر هم‌راستایی schema یا بررسی سلامت شکست بخورد، update.sh خودش سرویس را ری‌استارت نمی‌کند و بکاپِ همان لحظه را برای `sudo bash deploy/update.sh --rollback --yes` معرفی می‌کند.

اگر دکمهٔ پنل `pull` کند اما هنوز حلقهٔ گیت (بخش ۵) راه نیفتاده باشد، `git pull` خطا می‌دهد و استقرار اجرا نمی‌شود؛ اول بخش ۵ را انجام دهید یا `ops.console.deploy_cmd` را روی `deploy/update.sh --no-pull` بگذارید.

## ۴) نمایش لاگ سرویس

- بدون تنظیم: `~/.pm2/logs/nobino-api-out.log` و بعد `nobino-api-error.log` امتحان می‌شود.
- اگر مسیر لاگ‌تان جای دیگری است، در `.env` سرور بگذارید و سرویس را ری‌استارت کنید:

```bash
printf 'OPS_CONSOLE_LOG_FILE=/root/.pm2/logs/nobino-api-out.log\n' >> .env
pm2 restart nobino-api --update-env
```

## ۵) حلقهٔ گیت — دسترسی ویرایش فایل برای دستیار (یک‌بار راه‌اندازی)

به‌جای endpoint نوشتن فایل (که اگر لو برود یعنی کنترل کامل سرور)، از push گیت استفاده می‌شود: هر تغییری اول کامیت است، قابل بازبینی است و rollback دارد.

**روی سرور** (یک‌بار):

```bash
sudo bash deploy/install-git-remote.sh
```

این اسکریپت یک مخزن bare در `/var/repo/nobino.git` می‌سازد و هوک `post-receive` می‌نویسد که بعد از هر push به `main`، فایل‌ها را در پوشهٔ اپ چک‌اوت کند و `deploy/update.sh --no-pull` را خودکار اجرا کند. فایل‌های gitignored (`.env`، `backups/`، `logs/`) هرگز دست نمی‌خورند.

**روی سیستم خودتان** (که کلید SSH سرور را دارد):

```bash
git remote add deploy root@<IP>:/var/repo/nobino.git
git push deploy main
```

از این پس، هر `git push deploy main` = استقرار کامل روی سرور (خروجی: تب «عملیات» یا `logs/ops-deploy-last.log`). برای دادن دسترسی به من کافی است همین remote (آدرس + دسترسی SSH) را در اختیارم بگذارید.

نکته‌ها:

- push را با کاربری بزنید که حق نوشتن در پوشهٔ اپ را دارد (نصب‌کننده با root اجرا شده؛ root کافی است).
- تغییر دستی فایل روی سرور با push بعدی بازنویسی می‌شود؛ تغییرات را در مخزن محلی کامیت کنید.
- اگر در وسط استقرار، push دیگری برسد، هوک هم‌زمان دو استقرار را صف می‌کند؛ بین pushها فاصله بگذارید یا از دکمهٔ پنل (که استقرار هم‌زمان را رد می‌کند) استفاده کنید.

## ۶) متغیرهای محیطی (فقط در .env سرور)

| متغیر | پیش‌فرض | کار |
| --- | --- | --- |
| `OPS_CONSOLE_APP_ROOT` | پوشهٔ کاری پروسه | ریشهٔ پروژه برای گیت/دیسک/استقرار |
| `OPS_CONSOLE_LOG_FILE` | لاگ PM2 | فایل لاگ نمایش‌داده‌شده |
| `OPS_CONSOLE_RATE_PER_MINUTE` | 20 | جایگزین env برای سقف وضعیت/لاگ |
| `OPS_CONSOLE_DEPLOY_PER_HOUR` | 3 | جایگزین env برای سقف استقرار |

## ۷) محدودیت‌ها

- روی ویندوز توسعه، `pm2` و `df` در دسترس نیستند (کارت‌ها «در دسترس نیست» نشان می‌دهند) و دکمهٔ استقرار معنی ندارد — این ماژول برای سرور لینوکسی است.
- محدودساز نرخ درون‌فرایندی است؛ در PM2 با یک پروسه (حالت پیش‌فرض این استقرار) دقیق عمل می‌کند.
- هنگام ری‌استارت سرویس در میانهٔ استقرار، پاسخ HTTP دکمه قطع می‌شود (طبیعی است)؛ وضعیت را از تب عملیات دنبال کنید.
