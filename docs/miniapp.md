# مینی‌اپ پیام‌رسان‌ها (نسخهٔ `/mini`)

ماژولی سبک و تمام‌صفحه برای داخل وب‌ویو پیام‌رسان‌ها (بله، تلگرام، ایتا، وایتا) و
همین‌طور مرورگر عادی. دو کار را با هم انجام می‌دهد:

- **مشتری**: دیدن سالن خودش (توضیحات، تازه‌ترین پکیج‌ها، آرایشگران، ساعات کاری، نظرات،
  راه‌های تماس) و انتخاب روز و ساعت و ثبت نوبت.
- **صاحب سالن**: آمار روزانه، نوبت‌های هر روز، تأیید / انجام شد / لغو.

**مینی‌اپ سالن‌محور است، نه فهرست سالن‌ها.** در `/mini` هیچ جست‌وجو یا لیستی از
سالن‌های دیگر وجود ندارد: صاحب سالن فقط سالن خودش و مشتری فقط سالنی را می‌بیند که
از آن نوبت گرفته است. تشخیص «سالن صفحهٔ خانه» در `lib/resolve.ts` و به این ترتیب است:

1. اسلاگ داخل لینک پیام‌رسان — `/mini?salon=mah` (یا `slug`، `s`، `startapp`، `startparam`)
2. سالن خود کاربر، اگر `SALON_OWNER` باشد — `GET /api/dashboard/stats` → `stats.slug`
3. آخرین سالنی که کاربر از آن نوبت گرفته — `GET /api/appointments?limit=1` → `appointments[0].salonSlug`
4. سالن پیش‌فرض که سوپرادمین ست کرده — کلید `miniapps.default_salon`

اگر هیچ‌کدام پیدا نشد، صفحهٔ خانه فقط متن «سالنی برای نمایش نیست»، دکمهٔ ورود و
شمارهٔ پشتیبانی را نشان می‌دهد و **هیچ سالن دیگری فاش نمی‌شود**.

همه‌چیز از پنل سوپرادمین تنظیم می‌شود؛ هیچ فایلی خارج از پوشهٔ ماژول تغییر نکرده
مگر چند نقطهٔ اتصال (_mount_ در `App.tsx`، بخش تنظیمات، و اصلاح کوچک API مشترک).

## ۱) آدرس و مسیرها

| مسیر | محتوا |
|------|-------|
| `/mini` | خانهٔ سالن‌محور: سربرگ سالن، دربارهٔ سالن و راه‌های تماس، تازه‌ترین پکیج‌ها، تیم، ساعات کاری، نظرها، دکمهٔ رزرو |
| `/mini/s/<slug>` | رزرو همان سالن: خدمت (از خانه پیش‌انتخاب می‌شود: `?service=<id>`) → آرایشگر → روز → ساعت → ثبت نوبت |
| `/mini/appointments` | نوبت‌های من (پیشرو / گذشته) و لغو |
| `/mini/manage` | مدیریت سالن (فقط نقش‌های `SALON_OWNER`، `AGENT`، `ADMIN`) |
| `/mini/me` | حساب: اطلاعات تماس، تعداد نوبت، اتصال حساب پیام‌رسان، خروج |

آدرس کامل را خودِ بک‌اند از `miniapps.base_url` (یا `SITE_URL`) می‌سازد و در
`GET /api/mini/config` با فیلد `miniUrl` برمی‌گرداند.

ساختار پوشه‌ها:

```
frontend/src/mini/
  MiniApp.tsx        پوسته: نوار بالا/پایین، مسیرها، دکمهٔ «برگشت» پیام‌رسان
  mini.css           استایل ماژول (کاملاً scoped زیر `.mini-root`)
  lib/bridge.ts      تشخیص پلتفرم، initData، هپتیک، بستن وب‌ویو
  lib/store.tsx      کانفیگ + نشست + سبد رزرو + توست (MiniProvider)
  lib/resolve.ts     زنجیرهٔ «سالن صفحهٔ خانه» (لینک ← سالن خودم ← آخرین نوبت ← پیش‌فرض)
  lib/format.ts      تاریخ شمسی، تومان، رقم فارسی، رقم روز هفته، نرمال‌سازی شماره
  lib/types.ts       تایپ‌های پاسخ API
  components/        ui.tsx، booking.tsx، login-sheet.tsx
  pages/             MiniHome، MiniSalon، MiniBookings، MiniManage، MiniMe
```

ماژول هیچ کامپوننتی از بقیهٔ سایت import نمی‌کند، `AuthProvider` سایت را مصرف نمی‌کند
و استایلش با `tailwind` صفحات اصلی قاطی نمی‌شود؛ به همین دلیل می‌توان آن را بدون
ریسک حذف کرد یا به دامنهٔ دیگری منتقل کرد.

## ۲) تنظیمات از پنل سوپرادمین

بخش **«مینی‌اپ پیام‌رسان‌ها»** در `پنل ادمین ← تنظیمات سیستم` (کلیدهای `miniapps.*` در
جدول `Setting`؛ مقادیر `secret` رمزنگاری‌شده ذخیره می‌شوند):

| کارت | کلیدها | اثر |
|------|--------|-----|
| تنظیمات پایه | `base_url`، `manage_tab`، `default_salon`، `featured` | آدرس پایه، نمایش تب مدیریت، **اسلاگ سالن پیش‌فرض صفحهٔ خانه**، اسلاگ‌های ویژه (فقط برای `GET /api/mini/featured`؛ مینی‌اپ دیگر فهرست نمی‌سازد) |
| ظاهر و برندینگ | `title`، `subtitle`، `accent`، `hero_text`، `support_phone`، `show_prices` | نام/زیرعنوان، رنگ اصلی (hex)، متن قهرمان، تلفن پشتیبانی، نمایش قیمت‌ها |
| ویژگی‌ها و امنیت ورود | `allow_booking`، `allow_reviews`، `require_login`، `silent_login` | روشن/خاموش بودن رزرو، نظرات، ورود اجباری، ورود بی‌حس |
| تلگرام / بله / ایتا / وایتا | `<p>.enabled`، `bot`، `app`، `link`، `token` | فعال‌سازی، نام ربات و نام اپ، لینک رسمی نصب، توکن ربات (فقط سمت سرور) |

`token` هرگز به کلاینت نمی‌رود؛ `GET /api/mini/config` فقط `enabled`، `installUrl` و
`silentLogin` را می‌فرستد.

`default_salon` تنها کلیدی است که «چه کسی چه چیزی می‌بیند» را عوض می‌کند: کاربری که
وارد نشده یا سالنی به حسابش وصل نیست، خانهٔ مینی‌اپ را برای همان سالن باز می‌کند.
خالی بگذاریدش تا در همان حالت، صفحهٔ خانه فقط کارت ورود/پشتیبانی نشان دهد.
مقدار نامعتبر (خارج از الگوی `[a-z0-9-]{2,40}`) مثل خالی رفتار می‌کند.

برای فعال کردن یک پیام‌رسان:

1. در پنل، `enabled` را روی «روشن» بگذارید و `bot` + `app` را پر کنید (یا `link` را مستقیم بدهید).
2. توکن ربات را از BotFather / پنل رباتِ همان پیام‌رسان در فیلد `token` ذخیره کنید.
3. آدرس `https://your-domain/mini` را به‌عنوان Mini App به ربات وصل کنید.
4. کاربر از طریق لینک `installUrl` وارد می‌شود؛ برای ایتا و وایتا چون استاندارد
   `initData` امضاشدهٔ تلگرام را ندارند، `link` را دستی از پنل پیام‌رسان وارد کنید.

## ۳) مسیرهای API ماژول

| مسیر | متد | توضیح |
|------|-----|-------|
| `/api/mini/config` | GET | برندینگ، ویژگی‌ها، `defaultSalon`، پلتفرم‌ها و لینک نصب |
| `/api/mini/session` | POST | ورود بی‌حس با `initData` (پاسخ: `linked` / `needsPhone` / `mode: otp` / خطای ۴۰۱) |
| `/api/mini/link` | POST | اتصال حساب پیام‌رسان به حساب نوبینو (نیازمند نشست) |
| `/api/mini/staff?slug=` | GET | آرایشگران فعال یک سالن، با خدمات مجازشان |
| `/api/mini/featured` | GET | سالن‌های انتخاب‌شده توسط سوپرادمین — برای صفحهٔ عمومی سایت؛ مینی‌اپ از آن استفاده نمی‌کند |

بقرهٔ کار (رزرو، ساعت خالی، نظرات، لغو، تغییر وضعیت، آمار) همان endpoint های قبلی سایت است:
`/api/salons/:slug`، `/api/salons/:slug/availability`،
`/api/salons/:slug/reviews`، `POST /api/appointments`، `GET /api/appointments`،
`POST /api/appointments/:id/cancel`، `PATCH /api/appointments/:id`،
`/api/dashboard/stats`، `/api/auth/otp/*`، `/api/auth/me`.
بنابراین قوانین سالن، قفل همزمانی نوبت، پیامک‌ها و کمیسیون در مینی‌اپ هم دقیقاً همان است.

`GET /api/salons/:slug` برای خانهٔ مینی‌اپ غنی‌تر شد: علاوه بر `services`/`hours`/`gallery`
حال `timezone`، `whatsapp`، `instagram`، `website`، `mapUrl`، `neshanUrl`، `baladUrl` و در
هر خدمت `category` و `createdAt` را هم برمی‌گرداند («تازه‌ترین پکیج‌ها» بر پایهٔ
`createdAt` مرتب می‌شود). `/api/salons/search` دیگر توسط مینی‌اپ صدا زده نمی‌شود.

## ۴) امنیت ورود

- امضای `initData` سمت سرور با `HMAC-SHA256` و کلید `WebAppData` چک می‌شود
  (`backend/src/lib/mini/webapp-data.ts`)؛ `auth_date` کهنه رد می‌شود.
- هیچوقت `initDataUnsafe` کلاینت ملاک هویت نیست؛ فقط رشتهٔ خام به سرور می‌رود.
- اگر امضا معتبر باشد ولی حسابی وصل نباشد، `needsPhone` برمی‌گردد و کاربر OTP می‌زند؛
  بعد از ورود، مینی‌اپ خودش `POST /api/mini/link` را صدا می‌زند تا دفعهٔ بعد بی‌حس وارد شود.
- ایتا و وایتا: `signedInitData: false` → فقط OTP.
- پیوند پیام‌رسان ↔ کاربر در همان جدول `Setting` با کلید
  `miniapps.link.<platform>.<externalUserId>` نگه داشته می‌شود (بدون تغییر schema).

## ۵) تست‌هایی که روی این نسخه اجرا شده

محیط توسعه (`backend` روی `:3100`، `frontend` روی `:5175`، دیتابیس استرس ۲۵۱ سالن):

- خانهٔ سالن‌محور: رندر با سالن پیش‌فرض (مهمان)، رندر با اسلاگ داخل لینک
  (`/mini?salon=…`)، دربارهٔ سالن + راه‌های تماس، «تازه‌ترین پکیج‌ها» با مرتب‌سازی
  `createdAt`، برچسب روز جاری در ساعات کاری، نظرها و دکمهٔ رزرو چسبان.
- پیش‌انتخاب خدمت: `/mini/s/<slug>?service=<id>` درست همان خدمت را در فرم رزرو انتخاب می‌کند.
- نبود هیچ راه دسترسی به سالن دیگر: در خانه نه جست‌وجو هست نه فهرست؛ تنها مسیرهای
  `/mini/s/…` از «سالن خودم» (مدیریت) و «سالن نوبت‌های من» (نوبت‌های من) باز می‌شوند.
- صفحهٔ رزرو: انتخاب خدمت، فیلتر آرایشگران مجاز، نوار ۱۴ روز، بارگذاری ساعت‌های خالی،
  شیت تکمیل نوبت، ثبت با موفقیت و نمایش کد پیگیری.
- نوبت‌های من: پیشرو/گذشته، وضعیت‌ها، و مسیر لغو (پیام خطای قانون سالن روی توست نمایش داده می‌شود).
- OTP: درخواست، کد توسعه، تأیید و صدور نشست؛ و ورود به‌عنوان `SALON_OWNER`.
- مدیریت: آمار، نوار ۷ روز، تغییر وضعیت نوبت از «در انتظار تأیید» به «تأیید شده».
- ورود بی‌حس: `initData` امضاشدهٔ آزمایشی → `needsPhone`، سپس `link` و سپس نشست کامل؛
  امضای دست‌کاری‌شده `BAD_SIGNATURE` و `auth_date` کهنه `INIT_DATA_EXPIRED` رد شد.
- تنظیمات زنده: تغییر `accent`، `title`، `default_salon`، `manage_tab` و `allow_booking`
  از جدول `Setting` بلافاصله روی همان صفحه اثر کرد (پس از سرری شدن کش ۸ ثانیه‌ای).
- `npx tsc --noEmit` (ماژول `src/mini`) و `tsc -p tsconfig.build.json` در `backend/` بدون خطا.

## ۶) نکات و محدودیت‌های شناخته‌شده

- `/api/appointments` و `/api/dashboard/stats` برای صاحب سالن **اولین** سالن او را
  ملاک می‌گیرند؛ همین سالن، صفحهٔ خانهٔ مینی‌اپ او هم می‌شود. صاحب چند سالن باید برای
  بقیه به پنل وب برود (رفتار قبلی سایت، تغییر داده‌نشده).
- خانه فقط یک سالن را نشان می‌دهد. اگر `default_salon` خالی باشد و کاربر نه سالن خودش
  را داشته باشد نه نوبتی، صفحهٔ خانه کارت «ورود / پشتیبانی» است — فهرست جایگزین نمی‌شود.
- ویرایش «نام/شمارهٔ جایگزین» در `/mini/me` فعلاً فقط در `localStorage` همان دستگاه
  می‌ماند، چون endpoint ویرایش پروفایل در این پروژه وجود ندارد.
- صفحه‌بندی «بارگذاری بیشتر» فقط در `/mini/appointments` مانده است (فهرست نوبت‌ها)؛
  خانه دیگر فهرستی برای صفحه‌بندی ندارد.
- رنگ `accent` فقط `hex` سه‌ یا شش‌رقمی پذیرفته می‌شود؛ ورودی نامعتبر به رنگ پیش‌فرض برمی‌گردد.

## ۷) پس از گرفتن این نسخه

```bash
node backend/scripts/gen-controllers.mjs   # ثبت /api/mini/* در controller ها
cd backend && npm run build && npm start
cd frontend && npx vite build
```

`manifest.json` این ماژول پنج مسیر `mini/*` را (به‌جز `mini/config` که از قبل بود)
افزوده و کنترلرهای تولیدشده هم به همان ترتیب بازتولید شده‌اند.

نسخهٔ «خانهٔ سالن‌محور» هیچ مسیر جدیدی اضافه یا حذف نکرد (فقط بدنهٔ چند handler موجود
غنی‌تر شد)، پس برای به‌روزرسانی لازم نیست `gen-controllers.mjs` را دوباره اجرا کنید؛
`npm run build` در `backend/` و `npx vite build` در `frontend/` کافی است. تنها تنظیم
جدید `miniapps.default_salon` است که با ذخیره در پنل ساخته می‌شود.
