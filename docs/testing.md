# تست‌های خودکار (Nobino-nest)

این کپی (NestJS + Vite) برخلاف کپی Next.js هیچ سطح تستی نداشت؛ اسکریپت‌های
`scripts/*.test.mjs` و `scripts/e2e-*.cjs` نسخهٔ Next در این مخزن وجود ندارند و
بازنویسی‌شان خواسته شده بود. چهار فایل زیر جایشان را می‌گیرند و با `node:test`
بدون هیچ وابستگی تست اضافه اجرا می‌شوند:

```
npm test            # هر چهار دسته (59 تست)
npm run test:wiring # فقط سازگاری manifest/کنترلر (سریع، بدون بیلد و دیتابیس)
npm run test:smoke  # منطق خالص + سرور ساخته‌شده
npm run test:seo    # تولید صفحات سئو (prerender) — بدون بیلد، بدون سرور
npm run test:deploy # مسیر بکاپ/بازگشت deploy/update.sh (با stubهای bash)
```

`npm run verify` هم به انتهایش `npm test` اضافه شده است، پس بیلد انتشار دیگر
بدون تست نمی‌گذرد.

## ۱) `scripts/wiring.test.mjs` — سازگاری سیم‌کشی بک‌اند

بدون سرور، بدون دیتابیس، بدون بیلد. چیزی که در این پروژه «فرار» است و با دست
آسان بهم می‌ریزد را می‌سنجد:

| تست | چه چیزی را می‌گیرد |
| --- | --- |
| شکل manifest | `url === /api/<path>` با تبدیل `[x] → :x`، یکتا بودن path/url/module، روش‌های معتبر |
| فایل روت | هر مدول `@/routes/api/…` فایلش هست؛ هیچ فایل روت یتیمی بیرون از manifest نمانده |
| exportها | به‌ازای هر `methods` یک `export function GET/POST/…` وجود دارد و متد اضافه export نشده |
| کنترلرها | مجموعهٔ `(متد، url)` هر کنترلر تولیدشده دقیقاً با manifest یکی است (یادت نرود `npm run gen:controllers`) |
| استثناها | فقط `pages.controller.ts` و `admin/ai/{status,test}.controller.ts` دستی‌اند؛ بقیه تولیدی |
| مسیرهای `/api` در کد | هر رشتهٔ `"/api/…"` در `frontend/src`، `backend/src` و `scripts` یا در manifest است یا در یکی از کنترلرهای دستی (یا `/api/health` که `ops-middleware` می‌دهد) |
| کران‌ها | هر `this.fire("…")` در `CronJobsService` مسیرش را در manifest دارد |

## ۲) `scripts/smoke.test.mjs` — منطق خالص + سرور واقعی

بخش اول روی خروجی بیلد بک‌اند (`backend/dist/lib/**`) است و تابع‌های تجاریِ
بدون اثر جانبی را می‌سنجد: هش/راستی‌آزمایی رمز، `PASSWORD_MIN`، نیمه‌شب محلی تهران
و اجزای روز، تعریف سقف پلن‌ها (`plan.limit.<PLAN>.<key>`، قالب «تا ۳ کارمند»،
ارقام فارسی)، سقف آپلود/CRM (نگاشت بایت↔مگابایت)، نامک سالن، نشانی سالن
(ساب‌دامین محلی، `/s/<slug>`، میزبان خودِ سالن و دامنهٔ VERIFIED/PENDING)،
تقویم جلالی (رفت و برگشت، `۱۳ آبان ۱۴۰۵`)، پنجرهٔ روز و صفحه‌بندی/قیمت، و
اوریجین نمایشی `site-origin` (`requestOriginOrNull`/`publicOrigin`): میزبان محلی
با پورت پذیرفته می‌شود، میزبان زیر `ROOT_DOMAIN` پذیرفته و هدر جعلی رد می‌شود،
بیرون از درخواست همان `SITE_URL` برمی‌گردد و `salonPublicUrl` روی `:3100` نشانی
`:3100` می‌دهد (بدون ساختن `mah.mah`).

بخش دوم `backend/dist/main.js` را با `SERVE_FRONTEND=1` روی پورت تصادفی بالا
می‌آورد و این را چک می‌کند:

- `/api/health?db=1` زنده است و همان پورت را گزارش می‌دهد؛
- نوک‌های عمومی ۲۰۰ می‌دهند: `/api/packages`، `/api/salons/search`،
  `/api/mini/config`، `/api/mini/featured`، `/api/public/upload-limits`
  (و سقف‌ها به‌صورت مگابایت به کلاینت می‌رسد)؛
- `/api/pages/home` برای لودرِ شناخته‌شده ۲۰۰ و `/api/pages/<ناشناس>` ۴۰۴ است (نه ۵۰۰)؛
- نشانی‌های سرو‌شده با پورتِ میزبانِ درخواست ساخته می‌شوند: `/api/mini/config`
  با `Host: mah.localhost:3100` نشانی `http://mah.localhost:3100/mini` می‌دهد،
  با میزبان خودِ سرور همان پورت را نگه می‌دارد، و با `Host: evil.example.com`
  هیچ‌کدام از آن هاست در نشانی نمی‌نشیند؛ همان بررسی برای `publicUrl` لودر
  `/api/pages/dashboard-salon` هم انجام می‌شود (`http://<slug>.localhost:3100`،
  نه `/s/<slug>` روی `SITE_URL`)؛
- نوک‌های نگه‌داشته بدون توکن ۴۰۱ می‌دهند: `/api/salons`، `/api/admin/users`،
  `/api/admin/audit`، `/api/notifications`؛
- ورود سوپرادمین seed (`admin@nobino.ir` / `Admin@1234`) توکن می‌دهد و با همان
  توکن `/api/admin/users` و `/api/admin/ai/status` (شکل پاسخ: `switchOn` و
  `llmProviders[]` که `AiSettings.tsx` مصرف می‌کند) باز می‌شود؛
- SPA در `/` و fallback مسیر عمیق `/packages` کار می‌کند؛
- در لاگ بوت خطای حل‌ونصب Nest یا `UnhandledPromiseRejection` نباشد.

### حالت‌های skip (نه fail)

| شرط | رفتار |
| --- | --- |
| `backend/dist` نیست | همهٔ تست‌های این فایل skip می‌شوند؛ با `npm run build:backend` فعال می‌شوند |
| PostgreSQL بالا نیست | بخش HTTP skip با پیام «دیتابیس در دسترس نیست»؛ تست‌های خالص اجرا می‌مانند |
| `frontend/dist/index.html` نیست | فقط تست سرو SPA skip |

## ۳) `scripts/seo.test.mjs` — تولید صفحات سئو

`frontend/prerender.mjs` روی قالب `dist/index.html` کار می‌کند و خودِ همان فایل هم
با مسیر `/` بازنویسی می‌شود؛ یعنی اگر تگ‌های سئوی دور قبلی پاک نشوند، از دور
دوم به بعد همهٔ صفحات (۲۵۱ صفحهٔ سالن) چند `canonical` با هم دارند و خزندهٔ
گوگل اولی را می‌پذیرد — که canonical خانهٔ سایت است. این تست‌ها همان نقص را
می‌گیرند و تابع‌های خالص را بدون اجرای `prerender.mjs` می‌سنجند (فایل import شده
هیچ فایلی نمی‌نویسد و درخواستی نمی‌زند؛ فقط با اجرای مستقیم کار می‌کند).

| تست | چه چیزی را می‌گیرد |
| --- | --- |
| مبنای نشانی | `absPrefix`/`isLoopback` نشانی‌های `localhost`، `127.x`، `*.localhost`، `[::1]`، `::` و `0.0.0.0` را لوکال می‌شناسند (پیشوند خالی → لینک رلتی) و دامنهٔ واقعی را مطلق می‌گذارند؛ `PRERENDER_ALLOW_LOCAL=1|true` این را کنار می‌گذارد و `0` نه |
| هدر صفحه | هر صفحه دقیقاً یک `canonical`، یک `og:url`، یک `robots` و یک `title` دارد؛ `noindex` فقط برای صفحه‌های پنل؛ تصویر مطلق (`https://…`) دوباره پیشوند نمی‌گیرد |
| فرار HTML | عنوانی که `</title><script>` دارد به entity تبدیل می‌شود و تگ `script` تزریق‌شده باقی نمی‌ماند |
| idempotent بودن | سه اجرای پشت‌هم روی خروجی قبلی: تعداد canonical/og:url/robots/title همان ۱ می‌ماند و تایتلِ آخرین اجرا برنده است |
| دامنهٔ کهنه | canonical با دامنهٔ دیگری که در قالب مانده باشد پاک می‌شود |
| JSON-LD و noscript | در اجرای مجدد روی هم جمع نمی‌شوند؛ هر کدام یکی می‌ماند |
| تگ‌های غیرسئویی | `manifest`، `icon`، `charset` و تگ ماژول SPA هرگز پاک نمی‌شوند و هدر قبل از `</head>` می‌آید |

## ۴) `scripts/deploy-update.test.mjs` — بکاپ و بازگشت در `deploy/update.sh`

اینجا کد بک‌اند سنجیده نمی‌شود؛ کنترل جریانِ یک اسکریپت bash روی «سرور موهوم».
هر تست یک درخت پروژهٔ موقت می‌سازد (`package.json`، `prisma/migrations`،
`node_modules/prisma/build/index.js`)، `update.sh` را در آن کپی می‌کند و با
source کردن در یک subshell اجرا می‌کند؛ `git`، `sh`، `node`، `pg_dump`،
`pg_restore`، `pm2`، `curl` و `sleep` به تابع‌هایی تبدیل می‌شوند که فقط argv را
در یک لاگ می‌نویسند، و تابع `command` هم ربوده می‌شود تا با `W_MISSING` بتوان
نبودن یک ابزار را شبیه‌سازی کرد و ابزار واقعیِ سیستم هرگز صدا زده نشود.
ترتیب مراحل از روی همین لاگ خوانده می‌شود. اگر `bash` در PATH نباشد (ویندوز بدون
Git Bash) کل دسته skip می‌شود.

| تست | چه چیزی را می‌گیرد |
| --- | --- |
| سالم بودن فایل | `bash -n deploy/update.sh` خطای سینتکس ندهد |
| راهنما | هر گزینه‌ای که پارسر می‌پذیرد در خروجی `--help` هم مستند است و `--help` کد را چاپ نمی‌کند |
| گزینه‌های بد | `--frobnicate`، `--keep` بدون مقدار و `--keep abc` با کد 1 رد شوند و هیچ دستوری اجرا نشود |
| dry-run | خط `[dry] pg_dump` نشانیِ پاک‌شده دارد (`--dbname=` بدون `?schema=`) و هیچ دستور تغییردهنده‌ای اجرا/پوشه‌ای ساخته نمی‌شود |
| رمز مخفی | در `--dry-run` (هم ارتقا، هم بازگشت) هیچ جا رمز `.env` چاپ نمی‌شود (`postgresql://user:***@host/db`)، ولی در اجرای واقعی `pg_dump` همان نشانی کامل را می‌گیرد — مخفی‌سازی فقط نمایشی است؛ رمزی که خودش `@` دارد هم تا آخرین `@` مخفی می‌شود |
| ترتیب امن | `pg_dump` قبل از `migrate deploy` و قبل از `pm2 restart` اجرا می‌شود؛ `dump` و `.meta` (با commit و نام دیتابیس) روی دیسک می‌نشینند |
| `--backup-dir` | بکاپ در مسیر داده‌شده است و پوشهٔ پیش‌فرض (`backups/`) ساخته نمی‌شود |
| چرخش | با `--keep 2` و ۳ بکاپ قبلی، دقیقاً ۲ جفت dump+.meta می‌ماند و کهنه‌ترین حذف می‌شود |
| `--no-backup` | هشدار می‌دهد، `pg_dump` اجرا نمی‌کند و ارتقا ادامه می‌یابد |
| نبود `DATABASE_URL` | می‌ایستد؛ بکاپ نمی‌گیرد و ری‌استارت نمی‌کند |
| نبود `pg_dump` | می‌ایستد و `--no-backup` را پیشنهاد می‌دهد؛ پیش از تغییر schema |
| شکست migrate | سرویس ری‌استارت نمی‌شود و پیام مسیر بکاپ + `--rollback --yes` را نشان می‌دهد |
| rollback بی‌تأیید | در اجرای غیرتعاملی بدون `--yes` هیچ چیزی خراب نمی‌شود (نه `pm2 stop`، نه `pg_restore`، نه checkout) |
| rollback کامل | توقف سرویس → `pg_restore --clean --if-exists` با نشانی پاک‌شده → `git checkout <کامیتِ بکاپ>` → بازسازی و restart همان نسخه؛ بدون pull و بدون بکاپ از وضعیت خراب |
| درخت کثیف | rollback روی working treeِ ثبت‌نشده می‌ایستد تا کارِ کسی نسوزد |
| بکاپ دستی | `--rollback=<فایل دلخواه>` فقط دیتابیس را برمی‌گرداند و checkout کور انجام نمی‌دهد |
| dry-run بی‌ابزار | اگر `pg_dump` یا `DATABASE_URL` نباشد، `--dry-run` با هشدار نقشه را تا `[dry] curl …/api/health` ادامه می‌دهد و نشانی جای‌گزین چاپ می‌کند (اجرای واقعی همان‌جا می‌ایستد) |
| dry-run بازگشت | برنامهٔ `[dry] pg_restore --clean --if-exists` و بکاپِ درست‌انتخاب‌شده را نشان می‌دهد، بدون اجرای هیچ چیزی |

نتیجهٔ اجرای واقعی روی محیط توسعه: 59 تست (8 wiring + 21 smoke + 12 seo + 18
deploy). با بیلد تازه و دیتابیس محلی همه سبز؛ بدون دیتابیس فقط 9 مورد بخش HTTP
skip می‌شوند و 50 سبز باقی می‌مانند (تست‌های `deploy-update` مستقل از
دیتابیس‌اند و `DATABASE_URL` شل به آن‌ها نشت نمی‌کند).
